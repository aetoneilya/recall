# recall — design

Personal vocabulary trainer (English ↔ Russian for now) on spaced repetition. Words live in one SQLite database on a VPS. I review on an iPhone through a web app (installable PWA, also opens as a Telegram Mini App), add words by hand with an ✨ AI autofill, or have Claude propose them through a remote MCP server. A vocabulary-size estimate (a periodic Yes/No test, adjusted continuously by the words known in the app) shows where I stand. Next to the vocabulary, topic decks hold general Q&A flashcards (Java Core, Concurrency, Databases…) reviewed in the same session. A few users — the owner plus Telegram accounts on an allowlist — each with a fully separate collection.

## Layout

```
packages/core   shared TS: types (Word, Fact, Deck, Card, QueueItem…), FSRS wrapper (ts-fsrs), word → card faces, dedupe keys, word/fact cleaning, hierarchical tags (`tags.ts`), review-filter options (`facets.ts`), study-day math, typed-answer check. Source of truth for shapes.
server          Node 24 + Express 5 + node:sqlite. REST API, MCP endpoint, OAuth, Telegram bot, autofill (Anthropic SDK), vocabulary test, Decks importer.
server/data     en-freq.tsv, vocab-test.json, vocab-scale.json, packs/*.json (+ README.md, build scripts) — static data, all optional at runtime.
web             Svelte 5 + Vite. Review (typed answers), add word with autofill, the Cards tab (every card type of a deck), dashboard, vocabulary test. PWA + Telegram Mini App.
deploy          Caddyfile. Root Dockerfile + docker-compose.yml build one image serving web + API + MCP.
```

npm workspaces; `@recall/core` is imported as TS source (`exports: ./src/index.ts`). The server runs TS directly with Node's type stripping (`node --experimental-strip-types` is default in Node 24 — use `.ts` import specifiers, no enums/namespaces/parameter properties). Web bundles it through Vite.

On this machine npm and fetches go through a corporate proxy that breaks the public registry: run npm as `env -u HTTP_PROXY -u HTTPS_PROXY -u http_proxy -u https_proxy npm …`. `.npmrc` pins the public registry.

## Model

- **user** — a Telegram account: `telegramId`, `name` (Telegram first name), `timeZone`, `reminderTime`, `eveningReminderTime` (null = off). Defaults come from `TZ_NAME` / `REMINDER_TIME` / `EVENING_REMINDER_TIME` at creation; each user changes their own via `PATCH /api/me`. A row is created on the first successful sign-in. Who may sign in is configuration, not data: `OWNER_TELEGRAM_ID` (the admin) plus `ALLOW_USER_IDS`; anyone else is refused everywhere, and a user dropped from the list loses access with all their sessions and tokens.
- Every deck, word, card, review, vocabulary test and autofill counter belongs to exactly one user (decks, words and tests carry `user_id`; cards and logs through their word). Every query is scoped by the authenticated user, including by-id lookups: another user's id behaves exactly like an unknown id (404, skipped review), never 403. Dedupe is per user.
- **deck** — a big container ("English", "Programming") holding cards of any type: words, question/answer facts and grammar rules (facts with an exercise pool); subjects inside it (Java Core, Grammar, a book) are **tags**, not decks. `name` (unique per user, case-insensitive), `newPerDay` (default 15 for a deck with languages, 5 without), `reviewFilter` (below; null = everything). **Languages are optional**: `targetLang` / `nativeLang` (ISO 639-1, both or neither; unique per user by `targetLang`) — only a deck with them takes words, and only there do `forwardEnabled` / `reverseEnabled` (at least one on), `reverseAfterDays` (null = off) and `typeAnswer` apply; facts are always forward. The user's English deck is created on first use (`GET /api/decks`, adding a word, MCP). `defaultDeck` — where words go when no deck is named (REST, bot, autofill, dashboard, vocabulary test, MCP, weekly report) — is the `en` deck, else the first deck with languages, else a new English one. Lists order decks with languages first, then the rest, each by creation. The review session takes one deck at a time.
- **word** (`core/types.ts` `Word`) — `term` (base form as given: "to frown", "a far cry from"), `pos` (`noun | verb | adjective | adverb | phrasal_verb | idiom | phrase | preposition | conjunction | pronoun | interjection | other`), `translations` (≥ 1, main first), `ipa` (stored without slashes, General American from autofill; imported words keep whatever the source had), `examples` (≤ 5 × `{text, translation | null}`), `note` (usage, register, collocations — in the native language), `tags` (book / article / topic), `freqRank`, `cefr` (`A1…C2` | null), `status` (`active | rejected`; rejected = **dropped**: never shown, kept so the same word isn't added again), `createdBy` (`user | claude | import`). Everything added is `active` at once — app, bot, MCP, packs, imports; Claude's words also get the tag `claude` (`core.CLAUDE_TAG`), with no other mark and no limit of their own beyond the deck's new-per-day. Validation and cleaning: `core.cleanWord` (trims, dedupes translations/tags, strips IPA delimiters, limits in `core.LIMITS`).
- **fact** (`core/types.ts` `Fact`) — a question and its answer in any deck: `front`, `back` (both Markdown; the importer keeps Obsidian `[[wikilinks]]`), `tags`, `status` (`active | rejected`, as words; only active facts are studied), `createdBy` (`user | claude | import`). Cleaning: `core.cleanFact` (CRLF → LF, trailing spaces and blank edge lines dropped, Markdown inside kept; tags cleaned as below and deduped; limits `core.FACT_LIMITS`: front 2000, back 20000, 30 tags). Unique per deck by `core.factKey(front)`: NFKC, lowercased, spaces collapsed, trailing `?!.:;` dropped; a duplicate is `409 {error, existing}`. Exactly one card, direction `forward`. A fact can move to another deck (`deckId` in a patch) with its card and history; the target's questions count for the duplicate check. Claude's facts (MCP `add_facts`) are active at once and tagged `claude`, like words. A fact with ≥ 3 active exercises other than `write` is a **grammar rule** (derived, not stored: `factType`, the review filter's type `rule`). `FactItem.handbook = {topic, role: 'rule'|'card'}` when the fact comes from the grammar handbook pack (derived from `import_ref`, below).
- **Dedupe key** = deck + `core.dedupeKey(term, pos)`: the term lowercased, spaces collapsed, a leading "to " dropped, plus the part of speech — "to frown" and "Frown" (verbs) are one word, "frown" the noun is another. Enforced by a unique index; a duplicate add returns the existing word (REST `409 {error, existing}`; MCP lists it under `duplicates` with what differs). Dropped (rejected) words count, so a re-proposal is caught.
- **Tags** — free labels on words and facts. A tag with `/` is a **path**: `Grammar/Articles & nouns`, `Books/wuthering heights`, `Leon/phrases & collocations` (stored as full paths; the web builds the tree). Matching a filter or search tag `T` against a card tag `C` (`core.tagMatches`): `C === T` or `C` starts with `T + "/"` — so `Grammar` takes `Grammar/Tenses` but not `Grammarly`; case-sensitive. `core.tagAncestors('a/b/c')` → `['a', 'a/b']`, `core.tagLeaf('a/b')` → `'b'`, `core.tagParent('a/b/c')` → `'a/b'` (null at the top). Cleaning (`core.cleanTag`, used by `cleanWord` / `cleanFact` / `cleanReviewFilter`): each segment trimmed with spaces collapsed, empty segments dropped (`" a // b "` → `a/b`), case kept, ≤ 100 characters. Tags stored before this (e.g. `leon notes (спикинг) — phrases / collocations`) keep their text until retagged; naming one to rename or delete it matches its stored text exactly. Bulk rename / delete / add per deck: *Retagging* below.
- **freqRank** — computed by the server from `en-freq.tsv` (`server/src/lexicon.ts`): the term without "to ", parentheticals and punctuation is looked up by lemma with a light lemmatiser (the word itself, then plural -s/-es/-ies, -ed, -ing, -er/-est with e-restoration and undoubling, kept only if that stem is in the list). A multi-word term takes its **rarest** component's rank, or null if any component is missing (so "a broken bone" is null: "a"/"broken" are not lemmas in the list; irregular forms are not handled). Recomputed for all words at startup and whenever the list is (re)loaded (`syncFreqRanks`).
- **card** — belongs to a word (`wordId`) or a fact (`factId`), never both; one table, so review logs, undo, FSRS training, stats, the heatmap and the offline outbox treat both alike. Exactly two per word, `direction` `forward` (target → native, EN→RU, recognition) and `reverse` (native → target, production); created with the word, whatever its status. Holds the FSRS state (`CardState`). Editing a word never touches its cards, so history survives any fix. Suspending a word suspends both cards.
- **Verb forms** — `Word.forms?: {past: string[], participle: string[]}` (variants in each, General American first), computed by the server on every read from the irregular-verbs pack (`pack-data.verbForms`), never stored: a `verb` whose term without "to " is a pack verb, or a `phrasal_verb` whose first word is one (+ the particles: "to give up" → gave up · given up). Absent otherwise (the key is left out), and on words cached by older clients. `core.formsLine` → "began · begun", "learned / learnt · learned / learnt".
- **Faces** — `core.wordFace(word, direction)` → `{direction, front, back}`, each side a `FaceSide {term, ipa, posLabel, translations, example, exampleTranslation, note}` (fields that don't apply are null / []). forward: front = term + IPA + pos label; back = translations, first example + its translation, note. reverse: front = translations + pos label + the first example with the term blanked as `___` (`core.blankTerm`: case-insensitive, simple inflections -s/-es/-ed/-d/-ing/-er/-est, y→ies/ied, e-drop before -ing, consonant doubling; "someone/something/one's…" in idioms match any word); if the term isn't found, the example's translation instead; back = term + IPA + pos label + the full example (+ translation) + note.
- **Direction settings** — word cards only: a fact's card is always on, whatever the deck's directions. A disabled direction's cards are kept with their state and history but are invisible to the queue, deck counts, due forecast, stats and dashboard "known"; turning it back on restores them as they were. With `reverseAfterDays = N`, a word's *new* reverse card is only introduced once its forward card is out of the new state with stability ≥ N days (ignored while forward is disabled or that word's forward card is suspended); already started reverse cards are unaffected.
- **review_log** — every rating, with the state before/after. Client-generated UUID id → idempotent uploads.
- **Known** — a card is known when it is in review state with retrievability ≥ 0.9 now (`study.KNOWN_R`); a word is known when any of its enabled, unsuspended cards is. **Mastered** — every enabled direction's card in review with stability ≥ 21 days.

- **Per-user FSRS** — `requestRetention` (0.75–0.97, default 0.9) and `fsrsWeights` (null = defaults) per user; every server-side rating (`applyReviews`) uses them, the web reads them from `GET /api/me` for local scheduling. See *FSRS parameters*.
- **Deck `typeAnswer`** — `off | reverse | both`: whether the review screen asks to type the answer (only on reverse cards, or on both). Server-side setting returned with the deck (`DeckInfo = Deck & {typeAnswer, extraNewToday}` in `repo.ts`); the web acts on it.
- **Extra new today** — `POST /api/decks/:id/extra-new` ("+5 today") adds to a deck's allowance for the current study day only (`deck_extra_new`, keyed by `core.dayKey`); taps accumulate, the next study day starts from `newPerDay` again. `DeckInfo.extraNewToday` is that day's total (0 when none) — filled wherever the server knows the user's day (`GET /api/decks`, deck PATCH / extra-new / pack responses, MCP `list_decks`); internal reads that don't pass a day see 0.

Scheduling always goes through `core.review()`; never reimplement FSRS. The review engine is generic: it schedules cards, the word or fact is only what the face shows.

**QueueItem** (`core/types.ts`) is a union: `{kind: 'word', card, word, deckName} | {kind: 'fact', card, fact, deckName}`; `core.itemOf(item)` is the word or fact behind it (its id is what siblings share and burying keys on, its `deckId` the deck). Items cached by older clients have no `kind` and are read as words.

### Study day and limits

The user's `timeZone` (new users get `TZ_NAME`, default `Europe/Moscow`) and the global `DAY_START_HOUR` (default 4) define the study day (`core.dayKey`, read from the local wall clock: it starts at 4:00 local on DST days too). Due = `card.schedule.due < nextDayStart(now)` for learning/review cards (`core.nextDayStart` / `core.dayStart` step in hours, then quarter hours, so half- and quarter-hour zones such as India and Nepal get their own 4 a.m.). A new card (state 0) is never hidden by its due: its due is only its creation time (`newCardState(createdAt)`), and neither side drops or delays one because of it. New cards per deck per study day are capped by `deck.newPerDay` + that day's extra allowance (`extraNewToday`) minus new cards already introduced today (a card counts as introduced when its first review log falls in today). The budget is spent only on new cards the session will show: one buried by a sibling, of a disabled direction, outside the review filter or held back by the reverse gate never uses it, so "+5 new" always brings five showable cards while that many are left. Suspended cards, cards of non-active words or facts and cards of disabled directions are never queued. The session is one deck's due and new cards (words and facts mixed) that pass the deck's review filter; every deck is computed the same way, so each one's counts are known (the deck switcher, the bot). A deck's share doesn't depend on the others: the new budget is per deck and burying per word/fact.

**Review filter** (`deck.reviewFilter`, `core.ReviewFilter {types?: ('word'|'fact'|'rule')[], tags?, pos?, cefr?, directions?}`, cleaned by `core.cleanReviewFilter`; empty lists are dropped and an empty filter is null): what the deck's session takes. `core.inReviewFilter(f, card)` is **hybrid**: a card has one type, part of speech, CEFR and direction, so those **single-valued facets are OR** within the facet (B2 and C1 = cards at either level; Words and Grammar = both kinds); **tags are AND** (drill-down: tags A and B = cards carrying both), and a filter tag takes the tags under it (`core.tagMatches`: `Grammar` = any `Grammar/…` tag); facets AND with each other. `types` and `tags` apply to every card; `pos`, `cefr` and `directions` only to words — a fact is never excluded by them. Cards outside the filter wait as they are and use none of the day's new-card budget. (Filters saved under the earlier drill-down rule — AND within a facet too — can only widen under this one, so they were kept as they are.) Counts for a draft filter: `GET /api/decks/:id/review-options`.

### Queue order

Learning/relearning due now first, then review cards by due date, then new cards interleaved (one new after every ~4 reviews) in word/fact `createdAt` order across decks (forward before reverse). One card per word per day: siblings are buried until tomorrow — a card is skipped if the other direction was reviewed today or is earlier in the same queue.

**One rule set, both sides** (`core/today.ts`): the server (`study.selectQueue`: what it sends, counts and spends the budget on; the mock too) and the web (`queue.buildQueue`: what it shows) place every card with `core.planToday` → `core.todaySlot`, so a count never promises a card the session won't show. Cards go in queue order; for each:
- **buried** (out) — a new or review card when another card of its word/fact was reviewed today (server: today's review logs; web: also its own ratings not uploaded yet, `buried`) or was placed earlier in this queue; learning/relearning cards are mid-flight and never buried (but they bury their siblings);
- **new** (state 0) → **now**, whatever its due; asked of the day's budget last (`admitNew`), and a refused one buries nothing;
- a learning/review card due at or after the day's end → out;
- learning/relearning, or a card reviewed today and due again later today (its `lastReview` is today, or the web rated it here) → **later**: it waits for its due (the web's time-gated list);
- any other review → **now**.

Counts (`core.todayCount`): now + new → new, now + review → due, every later card → learning (learning cards that aren't due yet count as learning). The queue's `counts`, each `decks[].counts` (the deck switcher), `GET /api/decks/:id/review-options` counts and `GET /api/decks` `counts.new` all come from this placement; the web's `counts(queue)` gives the same numbers for the same items. (`GET /api/decks` `learning` / `due` stay deck-wide tallies for Progress, not the session's.)

**What the session shows next** (`web/src/lib/queue.ts` `nextItem`, pure, given the session's last ratings): (1) the first learning card that is due and rested, (2) else the first main card (reviews and new, server order), (3) else, learning ahead, the first learning card due within 20 min (`LEARN_AHEAD_MS`) that is rested and is **not the card just rated**, (4) else nothing — the waiting state. **Minimum gap** (`rested`): a card isn't shown again until 2 other cards have been rated since its last rating, or 60 s have passed since it (`GAP_CARDS`, `GAP_MS`), whichever comes first; the session keeps its last 8 ratings for this (`recent`, not persisted, cleared with the day). So the card just rated never comes straight back while another card is showable, two learning cards can't ping-pong every few seconds, and the card just rated is never learned ahead: it comes back at its own due. `upcoming` says which card comes next and when (by the same rules, nothing rated meanwhile), `peekNext` which card a rating of the current one brings (the stack shows it underneath). Undo bypasses all of it: the undone card is back at once, and the gap history goes back to before that rating. Undo takes back that one rating, not the queue: the card's state, its word's burying, the tally and the missed list go back to before it and the card goes on top of today's queue as it is now — a filter or direction changed since stays in force (a card it now leaves out isn't brought back).

IDs: short random base36 strings with a prefix (`us_`, `dk_`, `wd_`, `ft_`, `cd_`, `tk_`, `vt_`). Store hashes, never raw tokens. WAL mode, foreign keys on, migrations as an ordered list applied by `PRAGMA user_version`; each runs in one transaction with foreign keys off (table rebuilds need it) and must leave `PRAGMA foreign_key_check` clean, otherwise it rolls back and startup fails. A migration may have a `before` step that runs outside the transaction (the v3 backup: `VACUUM INTO` can't run inside one).

**v2 (multi-user)** rebuilds `decks`, `notes`, `sessions`, `oauth_tokens` with `user_id` (create new → copy → drop old → rename, so children's foreign keys keep pointing at the right name), recreates `oauth_codes` (in-flight codes are dropped), adds `users`, `api_tokens`, `login_nonces`. Existing rows — decks, notes, sessions, OAuth tokens — go to an owner user created from `OWNER_TELEGRAM_ID`; the bot's old `settings` keys (`telegram_chat_id`, `reminder_*_day`) move onto that user. If there are decks or notes and no `OWNER_TELEGRAM_ID`, startup fails with a message saying so and nothing is changed. Cards and review logs are untouched.

**v3 (words)** — flashcards become vocabulary. Before the transaction, a snapshot `VACUUM INTO <db dir>/backups/pre-v3-<ISO timestamp>.db` (skipped for `:memory:` and for databases without notes; `MigrationEnv.backupDir` overrides the directory). Then, per user (`users` ∪ deck owners):
- one deck "English" (`en` → `ru`, both directions on, `reverseAfterDays` null, `newPerDay` = the largest of the old decks that contributed words, else 15);
- **reversible** notes → words. The English side is found per note (`vocab-convert.englishSide`: the side without Cyrillic while the other has it, parentheticals ignored; mixed sides by Cyrillic share). Front English: ordinal 0 → `forward`, ordinal 1 → `reverse`; front Russian: swapped. FSRS state, suspension and card ids are kept, so are their logs;
- **basic** notes in a vocabulary deck (a deck with any reversible note, or named like vocab/словарь) whose sides are an English/Russian term pair (one line each, no markdown, English ≤ 10 words and not a question) → words; their card becomes the direction its old front asked (Russian front → `reverse`), the missing direction is a new card;
- fields: `term`/`pos` from the English side (`termAndPos`: a trailing "(adj.)"-style marker sets the part of speech and is removed; "to X up/out/…" phrasal_verb, "to X" verb, several words phrase, else `other`); translations from the Russian side, split on top-level ";" always and on "," only when every part is ≤ 4 words and none starts a subordinate clause ("как", "что", …); `extra` lines `IPA: /…/` (or a bare `/…/`) → `ipa`, the rest → `note`; tags kept except direction tags ("Russian → English"), the first breadcrumb-like tag (not a one-word plugin tag such as "vocab") → `source`; old `source` `decks:<ids>` → `import_ref`;
- **dedupe** across the old decks by the new key: translations merged (unique, order kept, a translation already present as comma pieces of another skipped), first IPA, notes joined, tags unioned, status active if any; per direction the card with more review logs (then more reps, then the earlier note) is kept, the other card is deleted with its logs; each merge is logged;
- everything else — cloze notes, basic Q&A (Revolut, grammar decks), unrecognisable pairs — is deleted with its cards and logs, and all old decks are dropped (approved by the user; the snapshot above is the way back). Then `notes`, old `cards` and `decks` are dropped and `cards_v3`/`decks_v3` renamed (review_logs keeps pointing at `cards`). `freq_rank` is filled at the next startup. The summary (words, merges, cards per direction with history, deleted notes by reason, logs kept/dropped) is printed and stored in `settings['migration.v3']`.

**v4** — `ALTER TABLE … ADD COLUMN` only (the columns above, with defaults) plus `bot_drafts`; no rebuild, no backup step, every row kept.

**v5** — `words.source` dropped: a non-blank source not already among the word's tags is appended to them (cut to 100 chars, unless the word already has 30 tags).

**v7 (exercises)** — new tables only (above); nothing else is touched, no backup step.

**v8 (tap exercises)** — `fact_exercises` rebuilt (create new → copy → drop → rename, after a `pre-v8` snapshot when it has rows) for the wider type CHECK plus `options` / `wrong`; every row, id, counter and dedupe key is kept, `exercise_attempts` keeps pointing at it by name.

**v9 (decks as containers)** — after a `pre-v9` snapshot (when there are decks), `decks` is rebuilt without `kind` / `in_review` and with `review_filter` (null), keeping every deck, id, name, languages and setting; words, facts, cards and logs are untouched. Words and facts still in the inbox become `active` (the inbox is gone). Topics don't become tags here: that is a merge (`merge-decks.ts`, below), run by hand.

**v10 (write items, extra new cards)** — `fact_exercises` rebuilt as in v8 (create new → copy → drop → rename, after a `pre-v10` snapshot when it has rows) for the wider type CHECK plus `rubric` (null for every existing row); every row, id, counter and dedupe key is kept, `exercise_attempts` keeps pointing at it by name and still cascades. `deck_extra_new` is new. Nothing else is touched.

**v6 (topic decks)** — before the transaction, `VACUUM INTO <db dir>/backups/pre-v6-<ISO timestamp>.db` (skipped for `:memory:` and databases without cards). `decks` and `cards` are rebuilt (create new → copy → drop old → rename, so `words` keeps pointing at `decks` and `review_logs` at `cards`): every deck becomes `kind = 'language'`, `in_review = 1`; every card keeps its id, word and state with `fact_id` null; indexes recreated (`decks_user_lang` partial on language decks). `facts` and `study_cards` are new. No other table is touched; `foreign_key_check` must stay clean. Ownership of a card is its word's or fact's: queue, reviews, undo, deck counts, stats, the dashboard heatmap and FSRS training read `study_cards`; word-only reads (dashboard vocabulary, leeches, vocabulary estimate, weekly report) keep joining `words`. A later migration that rebuilds `cards`, `words` or `facts` must drop and recreate the view.

## Auth

Every authenticated request resolves to a user (`req.user`); nothing implicitly means "the owner". Checked in this order:

1. **Telegram Mini App** — `X-Telegram-Init-Data` validated with `BOT_TOKEN` (HMAC per Telegram docs, `auth_date` ≤ 24 h); the Telegram id must be allowed. Creates the user on first sight and refreshes `name` from `first_name`. Wins over a cookie, since inside Telegram it is authoritative. A valid but not allowed id (and no other credential) gets `401 {error:'not allowed', telegramId}`.
2. **Session cookie** `recall_session` (`HttpOnly; SameSite=Lax; Secure` on https, 90 days) → its `user_id`. Issued by the bot login, the password fallback and the OAuth page's Telegram step.
3. **Bearer** (`Authorization: Bearer …`, on `/api` and `/mcp`):
   - the static `MCP_TOKEN` env → the owner (kept for the owner's existing Claude Code setup);
   - a **personal API token** `mn_…` → its user (`last_used_at` refreshed at most once a minute);
   - an **OAuth access token** → the user who approved it.

`OWNER_TELEGRAM_ID` is the admin: owns the pre-multi-user data, `MCP_TOKEN` and `OWNER_PASSWORD` sign in as them. `-dev` / `DEV=1`: no auth, everything runs as one dev user (Telegram id `OWNER_TELEGRAM_ID`, or `0` if unset).

### Log in with Telegram (PWA / browser, no initData)

1. `POST /api/login/telegram` → `{ nonce, url: "https://t.me/<bot>?start=login_<nonce>", expiresAt }`. The bot username comes from `getMe` at bot start; until then (or with the bot off) the route is `503`. Nonce: 128 random bits (22 base64url chars), stored as SHA-256, 5-minute TTL; 20 per IP per 15 min (`429`), at most 500 pending overall.
2. The user opens `url`; the bot gets `/start login_<nonce>`. Opening alone logs nobody in: if the sender is allowed and the nonce is live, the nonce is bound to that account (the first one to open it; anyone else gets "expired") and the bot asks "Log in to Mnemosyne on the web?" with ✅ Log in / ✖ Cancel buttons. Their callback data carries an opaque ref (the nonce's SHA-256, base64url), never the nonce. At press time the nonce must still be live and the presser must be the account that opened it; ✅ confirms it and the message becomes "✅ Logged in on the web — you can go back to the app", ✖ deletes it (the web's next poll gets `410`) and the message becomes "Cancelled". Strangers never get past the bot's allowlist check.
3. The web app polls `GET /api/login/telegram/:nonce`: `202 {status:'pending', expiresAt}` → `200 {status:'ok', user}` + `Set-Cookie` session, exactly once → afterwards (and for expired or unknown nonces) `410 {status:'expired', error}`.

Risk accepted: like any device-code flow, someone who gets an allowed user to open *their* link and press ✅ logs in as that user. The explicit question makes that a deliberate act rather than a side effect of tapping a link; the allowlist is a handful of friends.

### Password fallback

`OWNER_PASSWORD` env, owner only, for when Telegram is unreachable. `POST /api/login {password}` → session cookie for the owner. Constant-time compare, 10 failures per IP per 15 min.

### Personal API tokens

For Claude Code (`claude mcp add … --header "Authorization: Bearer mn_…"`) and scripts. `mn_` + 32 random bytes base64url (46 chars); only the hash is stored, the plaintext is returned once. At most 50 per user. Managed from a signed-in app (session, Mini App or dev) — not with a bearer, so a leaked token can't mint more.

### OAuth for claude.ai

The server is its own OAuth 2.1 authorization server, using the MCP SDK's Express helpers (`mcpAuthRouter`, `requireBearerAuth`) with an `OAuthServerProvider` implemented over the tables above:

- `/.well-known/oauth-authorization-server`, `/.well-known/oauth-protected-resource`, `/register` (dynamic client registration), `/authorize`, `/token`, `/revoke` — from `mcpAuthRouter`.
- `/authorize` shows a tiny server-rendered page. With a session cookie: "Allow <client> to manage your cards, <name>?" + Approve / Deny. Without one: a "Confirm in Telegram" button that runs the bot-login flow inline (shows the t.me link, polls, then submits Approve with the fresh session), plus the owner-password form as a fallback. PKCE S256 required. CSP allows only the page's own nonce'd script and same-origin fetches.
- Codes, access tokens (1 h) and refresh tokens (90 days, rotated) carry the approving user's id; `verifyAccessToken` passes it to `/mcp` in `authInfo.extra.userId`. A token issued for one user never acts as another.

```ts
  coverage: {from, to, words, known}[],   // rank bands 1-1000, 1001-2000, 2001-5000, 5001-10000, 10001-20000, 20001-30000
  vocabulary: VocabularySummary,
}
```
- `growth`: for each point t, a card's state is the `after` of its last review before t (a card without logs: its current state from `lastReview` on); a word counts if that state is review with R(t) ≥ 0.9 — the same "known" as now, reconstructed. Disabled and suspended cards are left out.
- `activity` (heatmap, streak, totals) counts every review of the user, words and facts in any deck; the rest of the dashboard is the language deck's words.
- `streak`: consecutive study days (user's zone) with ≥ 1 review, ending today, or yesterday if nothing yet today; `longest` over all history.
- `coverage`: distinct lemmas of single-word active terms with a `freqRank` in the band (multi-word terms are left out); `known` as above.

`VocabularySummary`:
```ts
{
  available: {frequencies, test, scale},             // which data files are loaded
  latestTest: (TestResult & {completedAt}) | null,   // latest valid completed test, as scored then
  current: VocabEstimate | null,                     // now: the latest test's band shares + today's known words; null without en-freq.tsv
  history: {testId, completedAt, estimate, adjusted, nativeEquivalent, reliability, valid}[],   // oldest first
  scale: {unit: 'lemmas', points: ScalePoint[], calibration: {adultSize, expectedInList, listSize}} | null,
}
VocabEstimate {
  estimate: number | null,      // in-list lemmas from the test alone (null without a test)
  interval: [lo, hi] | null,    // rough 95% interval of `estimate`
  adjusted: number,             // test ∪ app (below); without a test, the app's lower bound
  srsKnown: number,             // lemmas known in the app (hard lower bound)
  basis: 'test+app' | 'app',
  nativeEquivalent: {value, approximate: true},
  cefr: {level: ScalePoint|null, next: ScalePoint|null},     // learner points vs the in-list number
  scale: Record<'learner'|'native'|'fun', {level, next}>,    // learner vs in-list, native/fun vs nativeEquivalent
  perBand: {from, to, items, yes, hitRate, known /*test share, corrected + smoothed*/, srs /*app share*/}[],
}
ScalePoint {id, size, label, labelRu, emoji, group, range: [lo, hi]|null, approximate, source, url}
TestResult = VocabEstimate & {testId, falseAlarmRate, pseudowords: {items, yes}, answered, method: 'corrected'|'isdt'|'raw', reliability: 'ok'|'low', valid}
```

## Exercises (server/src/exercises.ts, import-exercises.ts, topup.ts; core/exercises.ts)

Grammar is practised through fresh items instead of a fixed card: FSRS schedules the **rule**, each review shows three items from its pool.

- **A rule is a fact with exercises**: front = the rule's title, back = the rule (Markdown), tagged `Grammar/<group>` in the English deck (the user's own also `Grammar/My rules`), plus a pool in `fact_exercises`. With ≥ `MIN_POOL` (3) active items other than `write` (`exercises.SERVABLE`) it reviews in exercise mode; otherwise it is a normal fact card. The Cards tab, editor, moving, history and MCP all keep working on it as a fact; `FactItem.exercises = {active, flagged, needsReview}` when it has a pool.
- **Items** (`core.ExerciseItem {id, type, prompt, answer, accepted[], explain, options?, wrong?}`; files and tools call the sentence `text`). **Tap types**, the ones served — answered with taps, no keyboard:
  - `choose` — `text` with exactly one `___`, 2–4 `options`, `answer` one of them (`—` = nothing there, the zero article);
  - `spot` — a sentence with one mistake; `wrong` = the wrong whole token(s), occurring exactly once (punctuation around a token doesn't count, `core.spotSpan`); 1–4 replacement `options` with the `answer` (`—` = delete it), never the wrong token itself.
  **Write** — `{type: 'write', prompt /*the task, in Russian*/, rubric? /*what a right answer must do*/}` (stored with `answer` '' and no options; `core.isWriteType`, keys `write:…`): the learner writes a sentence of their own, the server grades it with Claude (below). Never counted towards `MIN_POOL`.
  **Typed types** (legacy, still readable and reviewable): `gap` (one `___` + a hint in parentheses), `fix` (answer = the corrected sentence), `rewrite` ("sentence → cue ___"), with `accepted` variants. `core.cleanExercise` validates both families; `core.exerciseKey(text, type)` dedupes within a pool, per family (tap keys are prefixed, so a choose item may reuse a legacy gap sentence).
- **Grading** (on the device): tap items by identity — the option tapped is the answer; a spot item is right only when the mistake is tapped *and* the right replacement picked (a tap elsewhere is a miss at once). Typed items with `core.checkExercise`: strict — no typo tolerance — but case, spacing, quotes, punctuation and dashes don't count, and contractions equal their full forms both ways (`n't`, `'m`, `'re`, `'ve`, `'ll`; `'d` = would/had; pronoun + `'s` = is/has; won't, can't/cannot, let's). `core.exerciseRating(attempts)`: all right → Good, one wrong of two or more → Hard, else Again; items marked bad don't count.
- **Picking** (when the queue is built, `exercisesForQueue` → `pickForReview`): once a fact has ≥ 3 active tap items only those are served (typed ones never again); before that tap items come first and typed ones fill up. Within that: least recently shown first (never shown before anything), at most 2 of one type unless the pool has nothing else; ties are broken by a generator seeded with the card id, the study day and the card's `reps` (`exercises.reviewSeed`), so a refetch of the queue (or of practice) shows the same items until the card is rated, and the next day or rating draws anew. Write items join the tap items in that order only when the server can grade (`ANTHROPIC_API_KEY`; `/api/me.grading`), **at most one per review**; otherwise they are never picked. A review stays 3 items. Practice (`GET /api/practice`) picks the same way; `?fact=` draws up to 3 sets (at random), each from the items the earlier ones didn't use, topped up from used ones when the pool runs short (`exerciseSets`); whether the rule is tap-only is decided on its whole pool, never on the unused rest.
- **Grading write items** (`grade.ts`, `POST /api/exercises/:id/grade`): one structured call through autofill's `structuredCall` (same client, model, effort, fallback, 30 s timeout, and the **same per-user daily counter** `AUTOFILL_DAILY_LIMIT` / `autofill_usage` — a grade is one call). Input: the rule (fact front and back), the task and its rubric, the learner's sentence (≤ 500). Schema `{grammatical, usesRule, corrected, explain, score: 0|1|2}`: corrected = the sentence with minimal fixes (unchanged when right), explain = one or two sentences in Russian; `WriteGrade = {correct: score === 2, corrected, explain, score}`. Nothing is stored and the schedule is untouched: the outcome travels with the review's `exercises` attempts like any item (`correct` from the grade). The three items, answers included, go into the queue item (`FactQueueItem.exercises`), so a cached offline queue reviews them too.
- **Attempts**: the review's `ReviewInput.exercises` travel through the normal outbox (`given`: the option tapped; for spot "wrong → option", or the token tapped on a miss). On a newly applied review each item of that fact gets an attempt row and its counters (`shown_count`, `last_shown_at`, right / wrong — a bad item counts as neither); `overridden` ("I was right", typed items only) counts as right and sets `needs_review`; `bad` sets `status = 'flagged'` (out of the pool). Undo takes the counters back and deletes the attempts with the log; flags stay.
- **Import** (`node server/src/import-exercises.ts --file <rules.json> --db <recall.db> [--user <telegram id>] [--deck <name>] [--tag <root> (Grammar)] [--replace] [--dry-run]`): the file is a list of `{id, group, title, rule, fromNotes[], items[]}` (tap items `{type: 'choose', text, options, answer, explain}` / `{type: 'spot', text, wrong, options, answer, explain}`, or legacy typed ones), kept out of the repo (the owner's notes); next to `rules.json`, `rules.choice.json` and then `rules.reviewed.json` are read instead when they exist (a path naming one is read as given). Tap items get `import_ref <id>:tap:<n>`, typed ones `<id>:<n>`. `--replace`: a rule already imported that brings tap items first has its active typed items flagged out of the pool (counted as `replaced`), then gets the new ones; its fact, card, schedule and history stay. The deck is the English one unless `--deck` names another (created if missing). One fact per rule: back = rule + "**From your notes**" as a list (Obsidian `==x==` → bold), tags `[<root>/<group>, <root>/My rules]` with `--tag` as the root (default `Grammar`: `Grammar/Articles & nouns`, `Grammar/My rules`; no group → only `My rules`), `import_ref rules:<id>`, created in file order (= new-card order); items with `import_ref <id>:<n>`. Idempotent: an imported rule keeps its fact as it is and gets only the items it lacks; invalid items are reported, not imported.
- **Claude top-up** (`topup.ts`, only with `ANTHROPIC_API_KEY`): tap items only — write items neither count as fresh nor are listed to Claude, and none are generated. Hourly, a rule whose pool has fewer than 8 active never-shown items and no attempt in the last 24 h (`exercise_topups`) gets one structured call (autofill's `structuredCall`: same model, effort, fallback and per-user daily budget) asking for 15 **tap** items (choose / spot only), given the rule and every existing sentence: distractors from the rule's contrast set, exactly one grammatical option, no hint that translates or names the answer. Each item carries a `selfCheck {practisesTheRule, exactlyOneRight, noDistractorGrammatical, noGiveaway}`; kept only if all four are true, `cleanExercise` passes, the text has no parenthesised hint, and the sentence is new. Results are logged and stored per fact; a user at their daily limit is skipped for the rest of the pass.

## Content packs (server/src/pack-data.ts, packs.ts)

Ready-made card packs shipped as `server/data/packs/*.json`, loaded at startup from `DATA_DIR` and re-read when the files change (checked at most every 30 s); a broken file is logged and skipped. A file describes itself: `{id (lowercase-with-dashes), name, description, kind: 'topic', format, items}`, items in the order cards should be introduced. `kind` may be left out (it is always `topic`). Formats: `facts` — items `{key, front, back, tags?}` taken as they are; `irregular-verbs` — items `{verb, past[], participle[], translation, example: {text, translation}, note, rank}` (validated; Markdown characters in the data are refused), turned into facts at add time: front `**to begin**` + newline + the translation; back `**began · begun**` (all variants, `core.formsLine`), a blank line, the example in italics + newline + its translation, then the note; no tags (the deck name says it). The same data gives words their `forms`. `grammar-handbook` — items are topics `{id (lowercase-with-dashes), group, title, level (A1…C2), summary (Markdown cheat sheet), cards: [{front, back}] (3–6), exercises: [choose | spot items as in import-exercises' rules.json, `{type, text, options, answer, explain, wrong?}`] (≥ 3, each through `core.cleanExercise`, no repeated texts), write?: [{prompt, rubric?}]}`; anything invalid refuses the whole file (logged). Built from its parts by `node server/data/packs/build-grammar-handbook.ts <part-a.json> <part-b.json> [out]` (each part a list of topics or `{items}`; validated with `parsePack` before writing; default out `server/data/packs/grammar-handbook.json`).

- **Adding** (`addPack`): the deck is the one asked for, else the one the pack's earlier items went to (so a renamed deck keeps growing), else the default: irregular verbs and the grammar handbook → the English deck, any other pack → a deck with the pack's name (created if missing). Every item gets the pack's name as a tag, except the handbook's: per topic a **rule** fact (front = title, back = summary, tags `["Grammar/<group>"]`, `import_ref pack:grammar-handbook:<topic>`) and its theory cards as plain facts (the same tags, `…:<topic>:card:<n>`; the card type tells them apart). Cards added before tags were paths (`Grammar` / `Grammar theory` + a flat group) are left as they are on a rerun (idempotent by `import_ref`); the handbook read takes the group from either form. The owner's deck is retagged with the retag CLI (below). Then each handbook rule present gets the items it lacks: tap items `…:<topic>:ex:<n>` (there by import ref or by text), write items — the file's `…:<topic>:write:<n>`, topped up to 2 with generic tasks `…:<topic>:write:generic:<n>` (there by text only: the file's list can grow, so a position already held says nothing about a new item) («Напиши предложение, где нужно правило «<title>».», «Напиши вопрос или отрицание, где нужно правило «<title>».», rubric «Используй правило «<title>» правильно.»); `createdBy: 'import'`; a text the pool already has counts as there. So a rerun adds new topics and new exercises of old ones; a flagged item stays out (a deleted one comes back). Each missing item → an active fact, `createdBy: 'import'`, `import_ref = pack:<id>:<key>`, `created_at` = now + its index in ms: new cards are introduced by `created_at` (the queue's order), so they come most frequent first. Items already imported are skipped, as are questions the deck already has from elsewhere; a pack that grew later gets only its new items (after the old ones). One transaction.
- **Listing** (`listPacks`): per pack `{id, name, description, count, added (any item imported), missing (items an add would bring: not imported, and not a question the target deck already has), missingExercises? (handbook: items an add would bring to its rules), deckId?}`; the target deck is the one its items are in, else the default above (for the English-deck packs `defaultDeck`'s choice, without creating one).
- **Handbook read** (`handbook`, `GET /api/handbook`): the topics a deck holds and the user's own rules under `Grammar` (REST table above).

## Vocabulary size (server/src/vocab.ts, server/data/README.md)

Unit: English **lemmas within the 30,000-lemma list** of `en-freq.tsv`.

- **Test** — `POST /api/vocab-test` samples `itemsPerBand` (3) words from every 1000-rank band of `vocab-test.json` (30 bands, 1k…30k), skipping words the user already has in the app (by normalised term and lemma — those are known or not from the SRS), plus pseudowords at ~25 % of the items (`round(real × 0.25 / 0.75)`), shuffled. The items with the answer key are stored in `vocab_tests`; the client only gets `{id, word}`.
- **Scoring** (the file's `scoring`): h_b = share of band b's words ticked, f = share of pseudowords ticked (one f). known_b = max(0, (h_b − f)/(1 − f)) (correction for guessing; `isdt` = Huibregtse, Admiraal & Meara 2002 I_SDT per band, and `raw` = h_b, are selectable by the file). Bands without items take their neighbours' mean; the curve is then made non-increasing over bands (pool-adjacent-violators, weighted by items). `estimate = bandSize × Σ known_b`. `interval` = ± 1.96 × the combined binomial error of the band hit rates. `reliability: 'low'` when f > 0.2 or the overall hit rate does not beat f; `valid: false` (retake; never used as the latest test) when f > 0.5.
- **Adjusted** (README §4): per band `max(known_b, srs_b) × bandSize`, where srs_b = distinct lemmas of the band whose single-word term is known in the app / bandSize. The SRS count is a hard lower bound, so learning words raises the estimate between tests and a lucky test is never overruled. Recomputed on every dashboard read against the latest valid test.
- **Scale** (`vocab-scale.json`): learner points (CEFR, X_Lex ≤ 5k) compare against the in-list number; native and fun points against `nativeEquivalent = adultSize (42,000) × inList / expectedInList (26,686)` — approximate by construction (README §3: Brysbaert's 42k is on a larger list). Every point carries its `approximate` flag for the "≈".
- Data files are loaded lazily and re-read when they appear or change (checked at most every 30 s): without `en-freq.tsv` ranks and coverage are null/empty and `current` is null; without `vocab-test.json` the test routes are `503`; without `vocab-scale.json` placements are empty.

## Autofill (server/src/autofill.ts)

`POST /api/words/autofill` drafts a word from a bare term with the official Anthropic TypeScript SDK: `client.beta.messages.create` with `model` = `CLAUDE_MODEL` (default `claude-opus-5-5`), `output_config: {effort: 'low', format: {type: 'json_schema', schema}}` (structured outputs: `{draft: Sense, alternatives: Sense[]}`, every field required, nullable ones as `anyOf [..., null]`), `max_tokens` 8000 (thinking counts towards it), the server-side refusal fallback (`fallbacks: 'default'` with beta `server-side-fallback-2026-07-01`), and a client `timeout` of 30 s with the SDK's default 2 retries. System prompt: a bilingual lexicographer — base form, natural Russian translations by frequency, General American IPA without slashes, 1–2 natural examples with translations, a CEFR estimate, a concise usage note in Russian, other senses / parts of speech as alternatives (≤ 3). The answer goes through `core.cleanWord`; `duplicate` is the deck's existing word with the draft's key; `freqRank` comes from the list. Per-user limit `AUTOFILL_DAILY_LIMIT` (default 200) calls per study day, counted before the call (failures count too); token usage is logged and summed in `autofill_usage`. Off (`503`) without `ANTHROPIC_API_KEY`. Tests inject a fake client (`AppContext.autofill`). The bot's words and word picking (below), the exercise top-up and grading write items (*Exercises*) go through the same `structuredCall` and share that budget. An internal `context` (a sentence the term was met in) is passed as `Context: …`: it picks the sense and is made the draft's first example (`withFirstExample`: Claude's copy with its translation if it used the sentence verbatim, else the sentence with `translation: null`).

## FSRS parameters (server/src/fsrs.ts)

Trained per user with fsrs-rs through `@open-spaced-repetition/binding` 0.5.0 (napi-rs; prebuilt `.node` per platform as optional deps — `linux-x64-gnu` is an x86-64 ELF needing glibc ≥ 2.17, N-API so Node-version independent; no compiler on the server). Imported lazily: if it can't load, training is off with a warning and scheduling keeps working.
- **Data** — per card, its logs in order as `(rating, delta_t)` with delta_t = study days (user's zone, `DAY_START_HOUR`) since the previous review, 0 for the first and same-day ones; cards whose logged history doesn't start at state new (imports) are skipped. FSRSItems as Anki builds them: one per review after the first (the history up to it), kept when it holds a long-term review. `computeParameters(items, {enableShortTerm: true, numRelearningSteps: 1})` (ts-fsrs defaults: steps 1m/10m, relearning 10m). The binding's `timeout` option is not used — in 0.5.0 it makes the call never resolve.
- **When** — only with ≥ `FSRS_MIN_REVIEWS` (default 1000) usable reviews. A background pass every hour (first a minute after start) trains users with no attempt in the last 7 days and more reviews than the weights in use were trained on; `POST /api/fsrs/optimize` trains now, at most once per 24 h per user. One run per user at a time.
- **Adoption** — `core.sanitizeWeights` (exactly 21 finite numbers, then ts-fsrs `clipParameters`), then `evaluate` on the same items: log loss and RMSE must be ≤ those of the default weights and of the user's current weights. Adopted: `fsrs_prev_weights` ← old, `fsrs_weights`, `fsrs_trained_at`, `fsrs_reviews_used`; every attempt stores `fsrs_attempted_at` and `fsrs_result` (status, reason, metrics) and logs one line.
- **Use** — `userScheduler(db, userId)` = `core.scheduler({weights, requestRetention})`, used by `applyReviews`. "Known" (R ≥ 0.9) and other read-side retrievability still use the default weights.

## Telegram

grammY, long polling (no webhook needed). Only allowed users (owner + `ALLOW_USER_IDS`) get answers; others get "This is a private bot. Your Telegram id: N — send it to the owner to get access."

- `getMe` at startup (retried every 60 s if Telegram is unreachable) caches the bot username for the login links.
- `/start` — creates the user if needed, marks them as started (`bot_started_at`; their chat is their Telegram id), sets the chat menu button "Review" → Mini App (`APP_ORIGIN`), says hello by name with their counts. `/start login_<nonce>` instead asks "Log in to Mnemosyne on the web?" with ✅ Log in / ✖ Cancel inline buttons; the press confirms or cancels the web login (see Auth).
- Reminders, per started user, in their time zone: at `reminderTime` "N cards due" ("English 24 · Programming 5 due" when several decks have something) with a `web_app` button; skipped when nothing is due. The last sent study day is stored on the user so restarts don't double-send and a late start still catches up (until local midnight). A second nudge at `eveningReminderTime` (optional) if nothing was reviewed that day. Both times belong to the study day they fall in: with the day starting at 4:00, an evening nudge at 00:30 or a reminder at 02:00 comes at that time at the end of the study day, never at 4:00 of the next one, and doesn't use up the next morning. A user who blocked the bot (403) is skipped until the next `/start`.
- Due counts (reminders, `/due`, `/stats` "due today") are the review session's: every deck under its review filter, words and facts; the vocabulary numbers stay about words.
- `/due` — the sender's counts now. `/stats` — "📊 Vocabulary ≈ N words (CEFR)", known · mastered, streak (best), due today, with an "Open dashboard" button. `/help` — how to add words. Commands are registered with `setMyCommands` at start.
- **Weekly report** (`weekly.ts`) — per started user with `weeklyReport` on, at `weeklyReportDay`/`weeklyReportTime` (Sunday 19:00) local. The slot handled is stored as its local date (`weekly_sent_week`); a missed slot is still sent within 48 h, later (or one from before the user's `/start`) it is consumed silently. Rolling 7 days vs the 7 before, default deck: reviews (vs last week, %), new words, known (+change, from the growth reconstruction), streak, retention per direction (non-Again on review-state cards), vocabulary estimate (+change since the last report's), the 3 words with most Again, and one suggestion (a direction's retention < 80 % on ≥ 20 reviews → "try typing answers" unless that direction is already typed; no reviews; reviews down > 30 %; no vocabulary test in 60 days; inbox; few new words). Button "Open dashboard" → `#/dashboard`. Users without any words get nothing.

### Adding words by message (server/src/bot-words.ts, extract.ts, drafts.ts)

Private chats, allowed users only. What a text means (`parseMessage`):
- **a word / short phrase** (≤ 6 words, Latin letters, no `. ! ? ; :` except one trailing) → autofill (typing… shown) and added at once: `status: active`, `createdBy: 'user'`. Reply: `✅ <b>term</b> /ipa/ · pos · CEFR`, translations, one example + translation; buttons `✏️ Edit` (web_app `APP_ORIGIN/#/words/<id>`) · `✖`, and `↔ Other meaning` when autofill gave alternatives (cycles the word through them in place, skipping senses that collide with another word). ✖ deletes the word (drops it instead once it has been reviewed) → "✖ Removed: term". A `✅` on a message from before (the inbox) just confirms.
- **duplicate** (the draft's key exists, any status) → "Already in your deck: term — tr1, tr2 · new|learning|known|suspended|dropped"; if autofill found other translations, "Also: …" and `➕ Add translations` (also appends the context sentence as an example), otherwise no buttons.
- **no autofill / limit / refusal / error** → nothing is stored (translations are required, no placeholders): "Couldn't fill in term: <reason>. Add it in the app:" + web_app `✏️ Add in the app` → `#/words/new?term=<term>`.
- **word + context** — `term — sentence` (≥ 3 words with Latin letters) or a sentence with the word marked `*word*`, `"word"`, `«word»`, `“word”`, `_word_` → the sentence is sent as `Context:` and becomes the first example. `term — перевод` (no target-language sentence) is a `Hint:` instead.
- **several lines**, each one of the above (≤ 20; more → the first 20 and a note) → one "⏳ Adding N words…" message edited as each finishes ("… k/N"), then the list "✅ Added N words:" (+ duplicates and failures) with `✏️ Open in app` (`#/words`) · `✖ term` per word (deleted, or dropped once reviewed; struck through). After the limit or "not configured" the rest are not attempted.
- **anything else** (prose, > 1 line of prose, a paragraph) or a **photo** / image file (jpeg/png/gif/webp ≤ 3.75 MB; the largest photo size under that, via `getFile`, kept in memory only, sent as a base64 image block with the caption) → "🔍 Looking for words…", one structured call (`extract.ts`, same model/effort/fallback; counts as 1 on the daily budget). The prompt gives the learner's CEFR and vocabulary estimate and the rank below which words count as known (first frequency band with < 80 % known by test or app; 2000 without a test) and up to 600 deck terms to skip; the server then drops deck words (term or lemma), single words more frequent than that rank and repeats, keeping ≤ 12 `{term, pos, sentence, gloss}`. Reply: the numbered list with a toggle button per word (`✓ ` when selected) and `➕ Add selected (n)` → the batch flow above in the same message, each with its sentence as context and the gloss as hint. A link alone gets "I can't open links…".
- **Buttons** carry `<w|d|b|p>:<action>:<bd_ id>[:<index>]` (≤ 22 bytes); the draft holds the rest and is looked up by id *and* the presser's user id and kind, unexpired (7 days; expired rows are deleted whenever a draft is created). Anything else → popup "This message has expired — send the word again".
- Work runs in a per-user queue (`TaskQueue`) so the poller (grammY processes updates one by one) and other users aren't held up by a slow batch; tests await `queue.idle()`.

Bot is off when `BOT_TOKEN` is unset (and then Telegram sign-in is off too).

## Importer (server/src/import-decks.ts)

`node server/src/import-decks.ts --from <flashcards.db> --db <recall.db> [--user <telegram id>] [--topics <prefix>] [--dry-run]`. Vocabulary goes into that user's English deck, topic decks into plain decks (below) (default user `OWNER_TELEGRAM_ID`; the user row is created if missing, even on a dry run). Reads the Obsidian **Decks** plugin DB read-only (`decks`, `flashcards`, `review_logs`, `card_state_overlays`). Produces words directly, by the v3 migration's rules (`vocab-convert.ts`), so a fresh import gives what migrating an old import gives:

- `table` / `header-paragraph` rows are paired into one word: an `rcard_*` with its forward row (same breadcrumb, swapped front/back), or two one-way rows that mirror each other; table rows read their columns from `template_row` (a pronunciation column → `IPA: …`). A single row counts only in a vocabulary deck (one with pairs, or named like vocab) and when it looks like a term/gloss pair. Cloze and Q&A rows are skipped (counted).
- Each row becomes the card of the direction its front asks (English front → `forward`); a missing direction is a new card. State: `state='new'` → `newCardState`; `review` → CardState from `due_date`, `stability`, `difficulty`, `repetitions`, `lapses`, `last_reviewed`, `interval` (minutes → `scheduledDays`), `state: 2`. `review_logs` → `review_logs` with before/after built from `old_*`/`new_*`.
- The breadcrumb after the deck name (e.g. `wuthering heights`) is a tag (unless it is a direction section like "Russian → English"); Decks' own `tags` add more tags. `import_ref` = the comma-joined Decks ids.
- The same word twice in the import is merged (translations, per-direction card with more logs). Words active, `createdBy: 'import'`. Idempotent per user: rows whose Decks id is already in some word's `import_ref` are skipped; a word whose key already exists from elsewhere is counted as a duplicate and skipped. Log ids are Decks' own and global, so importing the same Decks DB into a second user skips its logs.
- **Topics**: Decks decks whose name starts with `--topics` (default `"Revolut — "`; `""` = none) are set aside before the vocabulary rules. Deck name = the rest of the name ("Revolut — Java Core" → "Java Core"), created if missing (without languages; an existing deck of that name is filled). To fold them into one deck as tags afterwards: `merge-decks.ts` (below). Each `header-paragraph` row → a fact: `front` = question, `back` = the Markdown answer as is (Decks `%%comments%%` stripped, wikilinks kept), tags = the prefix as a tag (`topicTag`: "Revolut — " → `revolut`) + the breadcrumb after the deck name + Decks' tags, `status: active`, `createdBy: 'import'`, `import_ref` = the Decks card id, `created_at` from Decks. Its card takes the row's state and suspension and its review logs exactly as a word's card does. Other rows of those decks (cloze, tables) and rows with an empty side are `skipped`. Re-running skips facts whose Decks id is already imported (their logs still map) and adds new ones; a question already in the deck from elsewhere counts as a duplicate.
- Prints `{flashcards, words: {created, merged, alreadyImported, duplicates}, cards: {forward, reverse, new, review, suspended}, logs: {imported, alreadyImported, orphaned}, skipped: {cloze, notWords, unsupportedType}, topics: {prefix, decks: {created, existing}, facts: {created, alreadyImported, duplicates}, cards: {new, review, suspended}, skipped}}`. A dry run (`--dry-run`) does everything in a transaction and rolls it back.

## Merging decks (server/src/merge-decks.ts)

`node server/src/merge-decks.ts --db <recall.db> [--user <telegram id>] --into <name> [--create-into] [--no-tag] [--dry-run] <deck name>…` — folds decks into one as tags (`repo.mergeDecks`, the same as `POST /api/decks/:id/merge`): every word and fact of each source moves into the target with the source's name as a tag (`--no-tag`: none); cards, schedules, history and exercise pools move with them; a word or question the target already has stays behind and is listed; an emptied source is deleted. Words go only into a deck with the same languages. `--create-into` creates the target (without languages) when no deck has that name; `--dry-run` rolls back. One transaction; prints a JSON summary. E.g. `--into Programming --create-into "Java Core" Concurrency Databases`, `--into English Grammar "Irregular verbs"`.

## Retagging (server/src/retag.ts, tags.ts)

`node server/src/retag.ts --db <recall.db> [--user <telegram id>] --deck <name> (--from <tag> --to <tag> [--only-with <tag>] | --delete <tag> [--only-with <tag>] | --map <file.json>) [--dry-run]` — the deck tag routes (`tags.retagDeck`, REST above) from the command line; `--user` defaults to `OWNER_TELEGRAM_ID`, opened and resolved as in `merge-decks.ts`; prints `{deck: {id, name}, steps: [{step, cards, words, facts}]}`; `--dry-run` rolls back. A mapping file is `{"about"?: note, "deck"?: name (else --deck), "steps": [step…]}`, applied in order in one transaction (a failing step rolls back all). Steps:
- `{"from", "to"}` — rename, as `POST …/tags/rename`;
- `{"delete", "exact"?}` — delete with descendants, as `POST …/tags/delete`; `"exact": true` removes only the tag itself (`Grammar`, not `Grammar/…`) and leaves the review filter alone (its tag still takes what is under it);
- `{"add"}` — as `POST …/tags/add`;
- each with optional conditions `"onlyWith"` (the card carries that tag or one under it, checked before the step) and `"source": "own" | "pack"` (`pack` = added from a content pack, `import_ref` `pack:…`; `own` = anything else).
Unknown keys are refused (a misspelt condition would widen a step). Running a mapping again is a no-op once applied.

`server/scripts/retag-english-2026-10.json` — the owner's English deck, October 2026: add `Grammar/My rules` to own cards tagged `Grammar` (the 20 rules from `import-exercises`, not the handbook's); rename `Grammar theory` → `Grammar` (theory cards, and a review filter on it); move each grammar group (the owner's and the handbook's) to `Grammar/<group>` only on cards carrying `Grammar` (a word tagged `Prepositions` stays); delete the plain `Grammar` (exact); book tags → `Books/<title>` (`the king in the yellow pt.1`, `wuthering heights`), `leon notes (спикинг) — <section>` → `Leon/<section>` with an inner ` / ` written ` & ` (`Leon/phrases & collocations`); delete `vocab` (on every word of the Decks import, so it says nothing). `claude` and `Irregular verbs` stay top-level. Tested on a prod-shaped fixture (`server/test/tags.test.ts`).

- **Fact editor** (`screens/FactEditor.svelte`, `#/fact/<id>`, `#/fact/new?deck=[&rule=1]`): deck (a select of every deck; changing it moves the fact on save), question, answer with an Edit / Preview switch (the card's rendering), tags; a duplicate question in the chosen deck shows inline as you type (from the cached facts; a server `409` fills in what the cache missed) with Open, and blocks saving. Card: state, due, stability, recall %, lapses, the last 16 ratings, Suspend / Resume. At the bottom Drop (or Restore for a dropped card) and Delete (undoable: `facts.deleteWithUndo`, the DELETE waits for the toast). Save in the bottom bar, and on the way out; offline the edit waits on the device (`lib/editOutbox.ts`) and shows at once. New mode: the deck from `?deck=`, else the last one used, else the one under review; "Add to <deck>" clears question and answer (deck and tags stay) and toasts with Undo. `rule=1` (the "+" picker's Grammar rule): "New grammar rule", tag `Grammar` preset; after the add it opens the new fact's editor at the exercise pool, which asks for at least three items.
- **`lib/markdown.ts`**: escapes the whole source first, then adds only its own tags: paragraphs (blank line) with `<br>` for single newlines — the document's first line, when it is nothing but `**bold**`, gets `class="lead"` and is set 1.36× (a pack verb's "to begin" and "began · begun"), `-`/`*`/`+` and `1.`/`1)` lists (continuation lines indented), `#` headings as bold lines, `---` rules, `**bold**`/`__bold__`, `*em*`/`_em_` (underscores only at word edges), `` `code` ``, ``` / ~~~ fenced blocks (verbatim, `data-lang`, SF Mono 13px, scroll sideways, bleed 10px into the card padding; swipes don't start on them), simple pipe tables (header, `---` row, rows; in a sideways-scrolling `.table-wrap`), inline code wrapping only at dots and camel humps (`<wbr>`), `[[target|alias]]` → the alias (or target, `#` as ›) as muted emphasised text. No links, images or raw HTML. Rendered with `{@html}`.
- **Typed answers** (deck `typeAnswer`: `reverse` = RU→EN cards, `both` = also EN→RU, typing the translation; missing → `off`): the action row becomes a field (`autocapitalize/autocorrect/spellcheck` off, `enterkeyhint=done`) + Check (reads "Don't know" while empty) + undo. Enter checks with `core.checkAnswer(input, word, direction)` (below); the card shows a verdict pill (Correct / Almost — a typo / Not quite / Didn't know) and, for close/wrong, your answer vs the closest accepted one with the differing letters marked (`core.answerDiff`). The suggested rating (exact → Good, close → Hard, wrong/empty → Again) is ringed on the bar; a second Enter takes it, any button or swipe overrides it. The field stays mounted and focused across typed cards (after the check it steps out of view but keeps focus; rating buttons don't steal focus; the next card renders synchronously inside the tap via `flushSync`), so the iOS keyboard doesn't drop between cards. The shell follows `visualViewport` (`lib/viewport.ts`: `--vv-h`/`--vv-top` size `#app`, `html[data-keyboard]` hides the tab bar), so the field and rating bar sit right above the keyboard without layout jumps.
- **`core.checkAnswer`** (`packages/core/src/answer.ts`): accepted answers = the term and its "/" or ";" alternatives (reverse) or every translation and its ","/";" pieces (forward), each also with parenthesised words dropped and kept ("take (it) easy"). Normalisation: NFKC, lowercase, ё → е, apostrophes dropped, hyphens/slashes → spaces, other punctuation removed, spaces collapsed; English also loses a leading "to" and article (a/an/the) and reads smb/sb/somebody → someone, sth/smth → something. Distance = Damerau–Levenshtein (OSA) to the closest accepted answer; tolerance by its length: ≤ 3 → 0, 4–6 → 1, 7–10 → 2, longer ⌈len/5⌉. Verdicts: equal → `exact`; within tolerance, or the input is an inflected form of the term ("frowned") → `close`; nothing typed → `empty`; else `wrong`. Returns `{verdict, distance, matched, suggestedRating}`.
- **Offline**: today's queue (server items + deck settings) in IndexedDB; ratings applied locally and queued in the review outbox → `POST /api/reviews` (on 5 pending, at the end, on hide, with backoff). Turning a direction off hides its cards on the spot. A new study day rolls over on start, on resume (visibility), on the waiting screen's tick and on the first rating, offline too: yesterday's burying, tally and missed list go and the queue is rebuilt; ratings not uploaded yet stay applied, also over a queue fetched across the turn. Words added offline (or when a POST fails on the network) go into `lib/wordOutbox.ts` (persisted; flushed with the reviews; a 409 on retry counts as done; refused words are dropped with a toast) and show "waiting to sync" on the add screen. The sync pill counts both. Service worker caches the shell. Edits in the word and fact editors that fail on the network go into `lib/editOutbox.ts` (one merged patch per card, persisted, flushed with the reviews; a refused one is dropped with a toast; a later online save of the card drops the fields it sent from the pending patch, so an older offline value never lands after it). A batch the server refuses with a 4xx is resent one review at a time, so only the bad one is dropped. An upload's answer doesn't overwrite a card rated (or a rating undone) here meanwhile. A new study day keeps the ratings made since the last fetch (they move into the cached queue) and drops yesterday's burying. **Per account**: every IndexedDB key lives under the signed-in user's id (`lib/accountKV.ts`; caches from before go to the first account seen); uploads wait until `/api/me` confirms the owner, again after any 401 (the next sign-in may be another account); another account signing in starts the app over under its own caches, and what the last one had pending stays under its id for its next sign-in; Log out flushes, then clears the account's caches (except what still has to upload; a write landing meanwhile doesn't bring them back). While the unowned caches move to the first account, reads and writes wait for it. One upload at a time (`flushNow` runs once more if asked meanwhile), so offline words and edits upload and toast once. A single failed IndexedDB write is logged and the store keeps working; only failing to open falls back to memory. Before an update reloads the page, queued IndexedDB writes are awaited (`update.setSettle`, ≤ 1 s). The account (`me`) is cached, so Settings shows it offline. A word queued offline can't be taken back once its upload has started (the Undo says so).
- **Add** (`#/add`, `#/fact/new`): a Word · Question · Grammar rule switch at the top (`components/AddTypeSwitch.svelte`, replaces the screen in place, remembered in `localStorage addType`; Word only for a deck with languages). **Add word**: one autofocused field "English word or phrase"; ✨ `POST /api/words/autofill` 600 ms after typing stops or on Enter (cached per term + context; stale answers ignored), with a pulsing sparkle and a skeleton meanwhile. The base form replaces what was typed ("frown" → "to frown"). Enter (in the term field, or on the empty translation field) or the bottom button adds: the form clears at once and the cursor is back in the field while the POST runs ("Added “x” · Undo" deletes it; a refusal brings the form back). Duplicates: autofill's `duplicate` or a `409` shows the existing word inline with "Add “…” to it" (PATCH merging translations and examples, Undo restores them) and Open; the same term under another part of speech (imported words are often `other`) gets the same panel, softer. 503 / 429 (autofill off for the visit) / 422 / 5xx / offline fall back to the empty fields with a one-line note; adding by hand always works.
- **Cards tab** (`screens/Words.svelte`, `#/words`): one deck's cards of every type, the deck from the same switcher as Review. ## Deploy

The VPS has no Docker and already runs nginx behind an SNI-routing front proxy, so: Node 24 + a systemd unit (`deploy/recall.service`, app in `/opt/recall`, DB in `/var/lib/recall`), an nginx `server` block on `:8444` (`deploy/nginx-exit.conf`), `scripts/deploy.sh` to rsync and restart. `node:sqlite` is built in; the one native dep, the FSRS optimizer, ships prebuilt binaries (`npm ci` on the host picks `binding-linux-x64-gnu` from the lockfile) and is optional at runtime. Nightly backup inside the server: `VACUUM INTO <db dir>/backups/recall-YYYY-MM-DD.db`, keep 14.

Connect Claude Code: create a personal token in Settings, then `claude mcp add --transport http recall https://<domain>/mcp --header "Authorization: Bearer mn_…"` (the owner's existing `$MCP_TOKEN` setup keeps working). claude.ai: Settings → Connectors → Add custom connector → `https://<domain>/mcp` (OAuth flow).
